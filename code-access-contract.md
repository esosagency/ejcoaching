# Codes personnels — contrat d’intégration

Projet /home/ubuntu/ejcoaching, React/Express/tRPC/Drizzle. Le propriétaire demande un vrai code par client, écran d’entrée dans le style Growth Capital (navy, halos violets, carte centrée, monogramme EJ), sans compte Manus client. Garder OAuth pour admin, clients et affectations, médias chiffrés, conversion vidéo. Aucun faux User/Manus JWT.

## Backend (agent dédié)

Possède drizzle/schema.ts et migration 0004 + snapshot/journal, shared/codeAccess.ts, shared/clientAccess.ts, server/clientCodes.ts, server/applicationAuth.ts, server/clientAccess.ts, server/clientRouter.ts, server/_core/context.ts, server/_core/trpc.ts, server/routers.ts, server/_core/oauth.ts et tests d’accès/codes. Ne pas modifier courseMedia.ts ni contentRouter.ts (parent), ni client/ (agent UI). Préserver les modifications existantes et ne pas appliquer les migrations ni créer des clients dans la base réelle.

`shared/codeAccess.ts` exporte `CodeClientIdentity={id:string,name:string,email:string|null,codeVersion:number}` et `ViewerProfile={id?:number,accountKey:string,name:string,email:string|null,role:'admin'|'user',clientId?:string}`. `AccessInfo.user` garde id optionnel et ajoute accountKey:string; pour admin accountKey=String(user.id), client accountKey='client_'+client.id. AccessInfo.clientId reste l’identifiant coachingClients. Aucun id numérique fictif pour client.

`authenticateApplicationRequest(req)` de server/applicationAuth.ts retourne `{user:User|null,client:CodeClientIdentity|null,hasClientCookie:boolean}`. Présence du cookie `ej_client_session` = mode client exclusif, même s’il est invalide/révoqué : jamais retomber sur l’admin injecté en Preview. Sans cookie client, appeler le SDK actuel et préserver le vrai admin. createContext inclut client?:CodeClientIdentity|null, hasClientCookie?:boolean pour compatibilité des fixtures. adminProcedure refuse client OU hasClientCookie; protectedProcedure accepte user ou client, permissions de cours ensuite explicites. auth.me renvoie ViewerProfile|null; auth.logout révoque/efface la session client, efface le cookie OAuth comme avant. Ajouter `clients.logout` public pour sortir du mode client avant l’entrée admin.

clientAccess exports compatibles : `getAccessForUser(user:User|null,client?:CodeClientIdentity|null)`, `getAssignedCourseIds(user:User|null,client?:CodeClientIdentity|null)`, `canAccessCourse(user:User|null,courseId:string,client?:CodeClientIdentity|null)`. Vérifier statut/codeVersion à chaque permission client; OAuth non-admin ne donne plus d’accès par courriel. Le principal client ne donne jamais admin. L’OAuth callback n’accepte plus que le vrai rôle admin.

Routes clients : me utilise user/client; approve garde retour {id}, accepte email vide/facultatif normalisé null et nom non vide; update et setStatus préservent révisions. adminList ajoute `codeEnabled:boolean`, `codeIssuedAt:string|null`, `lastCodeLoginAt:string|null` sans secrets. `clients.issueCode` admin mutation {id,revision} => {id,revision,code:string}; remplace aussi un code existant et révoque ses sessions. `clients.disableCode` admin mutation {id,revision} => {id,revision}; efface l’usage du code et révoque sessions. `clients.login` public mutation {code:string} => {success:true}; code brut dans corps seulement, cookie opaque HTTPOnly, SameSite=None/Secure HTTPS, 30 jours, aucune session dans JSON/URL. `clients.logout` public mutation {} ou sans input => {success:true}, révoque le jeton courant s’il existe et efface ej_client_session.

Colonnes coachingClients email nullable/contact uniquement; codeLookupHash unique nullable, codeVerifier nullable, codeVersion default0, codeIssuedAt nullable, lastCodeLoginAt nullable. Tables clientCodeSessions : tokenHash unique/pk, clientId FK, codeVersion, expiresAt, revokedAt, createdAt. Tentatives persistantes (clientCodeAttempts) à portée IP/empreinte de tentative, fenêtre bornée. Codes aléatoires EJ-XXXX-XXXX-XXXX à alphabet non ambigu, casse/espaces/tirets normalisés, vérification scrypt salée avec empreinte de recherche SHA256. Jamais codes/réponses sensibles dans les logs. Vérifier état/révision sous transaction lors d’émission, désactivation, révocation et création de session. Révoquer codeVersion/sessions sur suspension pour qu’une réactivation ne revive pas les anciennes sessions. Réponses login invalides génériques et limitations persistantes, requête contenant de très longs codes rejetée. Sessions opaques 32 octets aléatoires, stockées hachées et expirées. Pas de mot de passe ni email envoyé, aucun seed.

## Frontend (agent dédié)

Possède ClientGate.tsx/css, AdminClients.tsx/css, AccessContext, useAuth, const/main si nécessaire, App/LearningShell, accountStorage/LearningContext/Lesson pour les identités. Ne pas modifier server/ ou shared/ ou CatalogContext (parent). Utiliser les types temporaires du contrat au besoin, pas de tsconfig temporaire livré.

Écran /login pleine page et sans barre latérale, code seul, accessible et mobile, style premium sombre/violet de référence mais EJ original, placeholder EJ-XXXX-XXXX-XXXX et CTA « Entrer dans mon espace ». Aucun bouton de connexion Manus pour les clients, lien discret « Accès administrateur » qui efface le mode client puis utilise l’OAuth existant. /login doit permettre l’entrée d’un code même si le propriétaire est connecté en Preview. Connexion réussie : nettoyer caches des comptes puis navigation/rechargement vers /. Gérer erreurs réseau, code invalide, limites de tentatives, état occupé; ne pas afficher le code dans URL, storage ou journaux.

Gestion clients : nom, contact courriel facultatif, cours existants; créer le client puis bouton Générer le code. issueCode affiche le secret seulement dans un panneau éphémère avec Copier et Fermer, avertit que remplacer invalide l’ancien; pas de secret persistant/révélation d’ancien code. disableCode et statut révoqué accessibles avec confirmations. États sans code/actif/désactivé, historique dates sans empreintes. Sur fermeture/navigation enlever le code de l’état; ne pas enregistrer le code dans sessionStorage/localStorage.

ViewerProfile peut avoir id absent pour clients; comparer accountKey, jamais inventer id User. Clés de progrès/notes clients stables client_<id>, admin garde ses clés numériques historiques. Préserver l’éditeur/la caméra lors d’un recheck d’un même compte, cacher tant que permission non vérifiée; cache changement d’identité vidé. Parent adaptera CatalogContext aux requêtes {accountKey}.
